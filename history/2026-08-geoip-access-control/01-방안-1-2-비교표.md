# 방안 1·2 비교표

## 이 문서의 목적

이 문서는 결론을 미리 정하거나 새로운 문제를 만들기 위한 문서가 아니다. 고객이 직접 제시한 방안 1과 방안 2를 같은 조건에서 재현하고, 실제로 요구사항을 해결하는지 비교하기 위한 PoC 기준서다.

진행 순서는 다음과 같이 고정한다.

1. 고객이 제시한 방안 1과 방안 2를 원안에 가깝게 각각 구현한다.
2. 두 방안에 동일한 요청과 성공·실패 기준을 적용한다.
3. 구현 가능 여부, 요구사항 충족 여부, 운영상 차이를 증거로 비교한다.
4. 둘 중 하나가 적합하면 그 방안을 선택하고 3안을 만들지 않는다.
5. 두 방안 모두 핵심 요구사항을 해결하지 못할 때만 실패 원인을 근거로 방안 3을 설계한다.

현재 `terraform/` 코드는 이 비교 기준을 합의하기 전에 작성된 초안이다. 아직 방안 1, 방안 2 또는 방안 3의 정식 구현으로 판정하지 않는다.

## 고객 질문에서 확정된 내용

| 항목 | 고객이 제공한 내용 | PoC 반영 |
|---|---|---|
| 목적 | 국외 IP 차단과 VPN·Proxy 우회접속 방지 | 두 조건을 분리해 각각 판정 |
| 현재 인입 구조 | 고정 EIP 기반 NLB → Traefik | 두 방안의 공통 기준선으로 재현 |
| 적용 대상 | 문자서비스의 운영·테스트 엔드포인트 | 익명 PoC Host 2개로 재현 |
| 요청 경로 | `/SMS.asmx?WSDL` | 우선 고객 요청 그대로 시험 |
| 방안 1 | Traefik Middleware + MaxMind GeoIP | 별도 Terraform root로 구현 예정 |
| 방안 2 | NLB → ALB(WAF) → Traefik | 별도 Terraform root로 구현 예정 |
| 방안 2 비용 | 방안 결정 후 고객이 재문의 | 이번 기능 PoC의 판정 항목에서 제외 |

원본 자료에는 고객 식별 정보가 포함돼 있으므로 Git 이력에는 복사하지 않는다. 이 문서는 구조와 검증 질문만 익명화해 남긴다.

## 고객이 제시한 두 방안

### 방안 1 — Traefik Middleware + MaxMind GeoIP

```text
Client
  → 기존 형태의 Public NLB
  → Traefik
  → MaxMind 기반 Middleware
  → SMS test backend
```

고객이 기대하는 효과는 기존 NLB와 Traefik 구조를 유지하면서 필요한 Host·URI에만 국가 및 VPN·Proxy 차단을 적용하는 것이다.

### 방안 2 — NLB + ALB + WAF + Traefik

```text
Client
  → Public NLB
  → ALB + AWS WAF
  → Traefik
  → SMS test backend
```

고객이 기대하는 효과는 고정 EIP를 제공하는 NLB를 앞단에 유지하면서 WAF GeoMatch와 AWS 관리형 IP 평판 규칙을 사용하는 것이다.

## 1·2안 사전 비교

아래 내용은 최종 판정이 아니라 PoC에서 확인해야 할 차이점이다.

| 비교 항목 | 방안 1: Traefik Middleware | 방안 2: NLB → ALB + WAF |
|---|---|---|
| 정책 실행 위치 | EKS 내부 Traefik | AWS WAF |
| 기존 구조 변경 | Middleware와 DB 공급 구성이 중심 | ALB, WAF 및 NLB→ALB 연결 추가 |
| 실제 IP 판정 | PROXY Protocol 복원 IP를 플러그인이 사용하는지 확인 필요 | NLB→ALB를 통과한 IP를 WAF가 실제 client IP로 평가하는지 확인 필요 |
| 국외 IP 차단 | 국가 DB 조회와 차단 동작을 함께 검증 | WAF GeoMatch의 국가 판정을 검증 |
| VPN·Proxy 차단 | 선택한 MaxMind 제품과 플러그인이 Anonymous IP 정보를 실제 차단에 사용하는지 확인 필요 | 관리형 Anonymous IP/IP Reputation 규칙의 탐지 범위를 확인 |
| 데이터 갱신 | DB 다운로드·교체·재로딩 방식과 실패 동작 확인 | AWS 관리형 규칙 갱신을 사용하되 실제 룰 범위는 별도 확인 |
| 정책 범위 | 해당 Traefik router에만 연결 가능한지 확인 | 공유 ALB에서 Host·URI scope-down이 다른 서비스에 영향을 주지 않는지 확인 |
| TLS·전달 헤더 | 현재 NLB TLS 종료 및 PROXY Protocol과의 호환성 확인 | TLS 종료 위치 이동과 X-Forwarded-For 신뢰 경계 확인 |
| 배포 영향 | Traefik rollout 중 요청 오류와 DB 교체 실패 동작 확인 | NLB/ALB 연결, 인증서, 타깃 전환 과정의 영향 확인 |
| 롤백 | Middleware 제거와 이전 Traefik 설정 복원 | WAF/ALB 경로 해제와 이전 NLB 경로 복원 |
| 비용 | DB 제품·라이선스가 정해진 뒤 비교 | 고객 요청대로 최종 후보가 된 뒤 산정 |

## 공통 성공 기준

두 방안은 같은 조건을 모두 만족해야 `가능`으로 판정한다.

1. 국내 일반 IP 요청은 허용된다.
2. 국외 일반 IP 요청은 정책에 따라 탐지 또는 차단된다.
3. 시험에 사용한 알려진 VPN·Proxy·Tor 출발지는 별도 규칙으로 탐지된다.
4. 클라이언트가 위조한 `X-Forwarded-For`로 국가 또는 VPN 판정을 바꿀 수 없다.
5. 정책은 익명 SMS PoC Host와 `/SMS.asmx?WSDL` 요청에만 적용된다.
6. 같은 진입점을 공유하는 비대상 Host와 경로는 영향을 받지 않는다.
7. 정책 적용·갱신·rollout 중 정상 요청의 오류 여부를 관측할 수 있다.
8. 실패 시 기존 경로로 되돌릴 수 있고 롤백 증거가 남는다.

VPN·Proxy 탐지는 시험한 출발지와 해당 시점의 DB·관리형 룰 범위에 한해서만 성공으로 기록한다. 모든 VPN Endpoint를 완전히 차단한다고 확대 해석하지 않는다.

## 방안별 핵심 증명 항목

### 방안 1에서 반드시 답할 질문

| 질문 | 증거 | 실패 판정 |
|---|---|---|
| 선택한 Middleware가 국가를 조회하는 것에 그치지 않고 실제 403 차단까지 수행하는가? | Traefik 설정, 응답 코드, access log | 국가 헤더만 추가하고 요청을 허용 |
| Middleware가 NLB PROXY Protocol로 복원된 실제 client IP를 판정하는가? | 테스트 출발지 IP, Traefik client IP, plugin log | NLB/Pod 사설 IP를 국가 판정에 사용 |
| 국외 IP와 VPN·Proxy를 서로 다른 데이터로 판정할 수 있는가? | Country DB/Anonymous IP DB 종류와 탐지 결과 | 국가만 판정하고 VPN·Proxy 요구를 충족하지 못함 |
| DB를 갱신할 때 요청 오류나 장시간 중단이 없는가? | 갱신 전후 DB 버전, rollout 요청 결과 | 갱신·rollout 중 성공 기준을 넘는 오류 발생 |
| 문자서비스 router에만 Middleware를 연결할 수 있는가? | 대상·비대상 Host/URI 요청 결과 | 공유 서비스까지 차단 |

### 방안 2에서 반드시 답할 질문

| 질문 | 증거 | 실패 판정 |
|---|---|---|
| NLB가 ALB를 정상 타깃으로 사용하고 Traefik까지 요청을 전달하는가? | LB/TG health, HTTP 응답, 각 계층 로그 | 연결 불가 또는 지속적인 unhealthy |
| WAF가 NLB 주소가 아닌 실제 client IP를 기준으로 판정하는가? | 테스트 출발지 IP와 WAF `clientIp` 비교 | 중간 LB 주소를 client로 판정 |
| 위조 XFF가 WAF 판정을 변경하지 못하는가? | 정상/위조 요청의 WAF 로그 비교 | 사용자 제공 XFF로 국가 판정 변경 |
| GeoMatch와 Anonymous IP/IP Reputation 규칙이 각각 동작하는가? | WAF label/action 로그 | 국외 또는 시험 VPN·Proxy를 탐지하지 못함 |
| ALB 이후 Traefik이 올바른 scheme, Host, client chain을 받는가? | ALB·Traefik·backend 로그 비교 | 라우팅·TLS·client chain 손상 |
| 정책과 인증서 변경 범위를 SMS PoC Host로 격리할 수 있는가? | 대상·비대상 Host/URI 결과와 리소스 diff | 공유 서비스까지 변경 또는 차단 |

## 공통 증거 형식

각 요청에는 임의의 correlation ID를 넣고 다음 증거를 연결한다.

| 계층 | 기록할 값 |
|---|---|
| 테스트 클라이언트 | 실행 시각, 실제 공인 IP의 익명 토큰, 요청 ID, 응답 코드 |
| NLB/전송 계층 | listener/TG 상태와 실제 전달 방식 |
| 방안 1 | Traefik이 인식한 client IP, plugin 판정 국가·Anonymous 여부, 응답 코드 |
| 방안 2 | WAF `clientIp`, country, rule label/action, ALB client/target 정보 |
| Backend | Host, path, scheme, RemoteAddr, 전달 헤더의 익명화 결과 |

실제 고객 도메인, IP, 계정 ID, 인증서 ARN과 원본 access log는 Git에 저장하지 않는다.

## 판정 방법

각 방안은 다음 중 하나로만 판정한다.

| 판정 | 의미 |
|---|---|
| 가능 | 공통 성공 기준과 해당 방안의 핵심 증명 항목을 모두 만족 |
| 조건부 가능 | 핵심 기능은 동작하지만 DB 제품, 운영 절차, 구조 변경 등 명시된 조건이 필요 |
| 불가능 | 해당 구조 자체로 필수 요구사항을 충족할 수 없음 |
| 미확인 | 필요한 출발지, 로그 또는 환경이 없어 증거를 만들지 못함 |

최종 선택은 단순히 `동작함`만으로 결정하지 않는다. 두 방안이 모두 가능하면 다음 차이로 선택한다.

1. 고객의 전체 요구사항 충족 범위
2. 비대상 서비스 영향 범위
3. 운영자가 직접 관리해야 하는 DB·플러그인·갱신 절차
4. 변경과 롤백의 복잡도
5. 로그와 감사 증거의 명확성
6. 최종 후보가 된 이후의 비용

## 방안 3을 만드는 조건

방안 3은 지금 미리 설계하지 않는다. 다음 중 하나가 실제 결과로 확인될 때만 만든다.

- 방안 1이 국가 차단은 가능하지만 필수인 VPN·Proxy 요구를 충족하지 못한다.
- 방안 2가 실제 client IP를 WAF에 전달하지 못한다.
- 어느 방안이든 SMS 정책을 공유 서비스와 안전하게 격리하지 못한다.
- 두 방안 모두 고객이 허용할 수 없는 변경 또는 운영 부담을 요구한다.

방안 3의 요구사항은 1·2안의 실패 증거에서 도출하며, 별도의 새로운 문제를 추가하지 않는다.

## 구현 전 사용자 확인 항목

아래 항목은 임의로 결정하지 않고 사용자와 합의한 뒤 구현한다.

1. 첫 구현 순서: 방안 1부터 할지, 방안 2부터 할지
2. URI scope: 고객이 말한 `/SMS.asmx?WSDL`만 재현할지, 실제 SOAP 요청까지 포함해 `/SMS.asmx` 전체를 비교할지
3. VPN·Proxy 시험 출발지: 어떤 VPN, Tor 또는 cloud exit를 사용할지
4. 방안 1의 MaxMind 범위: 고객 원안 그대로 Country DB부터 시험할지, Anonymous IP 제품까지 포함할지
5. 현재 `terraform/` 초안을 방안 2 구현으로 수정할지, 폐기하고 새로 작성할지
